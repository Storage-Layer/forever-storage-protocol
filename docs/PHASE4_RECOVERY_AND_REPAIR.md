# Phase 4 Recovery & Repair
`DistributedRepairScheduler`: heartbeat polling -> blind observation (Healthy/Suspected/ConfirmedByPolicy/RecoveryObserved) -> `VerifyShard` per shard -> `AdaptiveStorageRepairPlanner` (Phase 2 v2 policy) -> deduplicated queue -> reconstruct from k remote shards, verify digest, PutShard to the same node if online else a replacement chosen by the planner, VerifyShard, re-sign manifest (generation+1). Queued repair is cancelled when the shard verifies healthy (node recovered). `BackgroundScrubber`: rate-limited VerifyShard sweep with nonce challenge, persisted cursor.
Honest caveats: the heartbeat-to-observation mapping (thresholds, posterior formula) is a simple heuristic in the scheduler, not the calibrated Phase 2 detector; the scrubber only checks that the challenge response is a 64-hex string and stripe count matches — it does **not** recompute the expected digest (the coordinator holds no copy of the container), so a node that lies about the challenge is not caught; repair inspects stripe 0 placements only; one manifest rewrite per repaired shard.
Benchmark recovery run: 8 of 22 nodes stopped, all 20 shards of a 1 MiB object enqueued; only 2 repairs succeeded, 6 failed (only 2 spare nodes remained, so replacement targets ran out) — expected capacity-limited behaviour, not a success of full repair.
